# CLI reference

Every read command supports `--json` with a stable, documented schema (coding agents parse it;
`/dev/schema/cli` serves the schemas in dev mode). `-d/--project-dir` defaults to the current
directory everywhere.

## Project

| Command | Options | |
|---|---|---|
| `tuvl init [NAME]` | `--sample`, `--preset gemini\|openai\|anthropic\|ollama`, `--decision-model laya\|none`, `-y/--yes`, `--multi-tenant`, `--no-ai-skills`, `--agent`, `--no-agent`, `--list-agents`, `--initials`, `--git/--no-git`, `--branch`, `--commit`, `--ci github\|gitlab\|none` | Scaffold a project. A preset writes `llms/default.yaml` with a current model id, reading the key from the environment. `--sample` is a ticket-triage project (spec, TaskPlan, tests, lock) that passes the CI gate as created. `--decision-model laya` adds `llms/laya.yaml`, `LAYA_API_*` in `.env` and a `compose.yaml` that runs laya-serve locally (asked interactively, default no). `-y` accepts every default. It also asks for your initials (they stamp the ids of ideas and specs you create) and, when coding agents are installed, which one tuvl may run for you (`-y` picks none), writes both to `.tuvl/agent.yaml` (git-ignored), and runs `git init` on branch `develop` when git is installed (`--ci github` or `gitlab` also writes the deterministic gate as CI: errors fail on pull requests, everything `--strict` on pushes to `develop`/`main`) and the project is not already inside a repository (`--commit` makes an initial commit) |
| `tuvl agent list` / `use <agent\|none>` / `test` | `-d`, `--json` (list), `--force`, `--command` (use) | The coding agents on this machine (Claude Code, Codex, Gemini CLI, Antigravity, Cursor, Copilot CLI, Amp, Qwen Code, Aider, OpenCode, Goose), the one you selected, and whether tuvl can run it: `yes` for an agent tuvl can let draft and build (Claude Code, Codex CLI, Gemini CLI: their headless modes can confine a write to the folder), `review only` for one it can ask to review but never to write (Cursor, Antigravity, Copilot CLI, Amp), `detected, not yet` for the rest. The choice is yours alone, in `.tuvl/agent.yaml` (git-ignored). `test` checks the selected agent starts, then runs it once on a trivial task in a scratch folder (a few tokens; `-y` skips the question). `use generic --command '…'` selects any command that reads a prompt on stdin and edits its working directory |
| `tuvl storage` | `check [name]`, `ls <name> [prefix]` | Check each `kind: Storage` store by writing, reading back and deleting a probe object (read-only stores are only listed), or list a store's objects. See `docs/storage.md` |
| `tuvl validate` | `--strict`, `--json` | Contracts, data flow, types, policy, artifacts, lock; prints each workflow's determinism profile and worst-case tokens. `--strict` fails on warnings. Ends with **needs models**: every model the workflows use, its provider and the environment variables it reads (or "no LLM required"); V028 = unknown model reference, V029 = undeclared credentials (an error at ship time) |
| `tuvl codegen [WORKFLOW]` | `--check` | Schemas, code-agent stubs (body-preserving merge), prompt placeholders, spec tests. `--check` writes nothing and exits 1 on drift |
| `tuvl codegen --spec SPEC --task 3 \| --task 1,3 \| --all` | `--no-agent`, `--agent`, `--max-attempts 3`, `--budget USD`, `--timeout S`, `--model`, `--base`, `--no-pr`, `--ready`, `--continue`, `--keep-worktree`, `--consent`, `--review none\|static\|agent`, `--review-blocking`, `--reviewer` | Build an **approved** spec's models and workflows from its task list. **Phase 1, deterministic, zero tokens:** the missing `models/*.yaml` from `# Data`, a `workflows/<flow>.yaml` skeleton whose steps are all `pending` (trigger, ends, and every step's id, inputs, outputs, routes and budget come from `# Flows`), then the generated schemas, stubs, prompt placeholders and tests; one branch `feature/<SPEC>-scaffold`, never overwriting an existing file. **Phase 2, your coding agent, one task at a time:** for each selected agent task a branch `feature/TASK-…` stacked on the one before, in a worktree; the agent replaces that one pending step and may touch only the workflow, `agents/*.py` and `artifacts/`; tuvl regenerates what is generated and accepts the task only when the step is implemented and `validate` and `spec verify` agree (findings go back to the agent), then commits and, with a remote and `gh`/`glab`, pushes and opens a draft pull request based on the previous branch. Before a task is committed its Python is reviewed (`--review static`, the default: the C-rules and ruff, errors fail the task and go back to the agent; `agent` adds a second opinion that lands in the pull request and blocks only with `--review-blocking`). Failed tasks leave no branch and stop the run (`--continue` goes on with independent ones). Re-running skips what is built. Task numbers: `3`, `T3`, `003` or the full id. `--no-agent` stops after phase 1. Without `--spec`, `tuvl codegen` is unchanged and never calls an agent |
| `tuvl review [PATH…]` | `--base REF`, `--strict`, `--no-ruff`, `--explain C0xx`, `--json`; second opinion: `--agent`, `--reviewer`, `--spec`, `--blocking off\|high\|medium\|low`, `--post`, `--consent`, `--budget`, `--timeout` | Review the Python of code agents (`agents/*.py`, not `_generated`). **Tier 1, free:** tuvl's rules — C001 shape (`@agent("run") async def f(inp, ctx)`), C002 processes and `eval`, C003 direct network (use `ctx.http`), C004 `os.environ`, C005 file writes (use `ctx.storage`), C006 non-determinism (random, uuid, clock), C007/C008 work or state kept in the module, C009 hard-coded URLs, C010 secrets, C011 a returned signal the workflow does not route, C012 a write in an `effect: read` agent — plus `ruff` (C900) when installed. Errors fail (exit 1), warnings only with `--strict`. **Tier 2, advisory:** `--agent` asks a coding agent that cannot change anything (Claude Code runs with only Read, Glob and Grep) to read the code, the diff and the spec and answer with JSON findings (high / medium / low / info); an answer that is not valid JSON is a failed review, never a pass. Findings only block with `--blocking`. `--post` comments the review on the branch's pull request. The reviewer is another agent than yours when you have one |
| `tuvl lock` | `--check`, `--mcp/--no-mcp` | Pin model ids, artifact hashes, judge/decision models and MCP tool schemas in `tuvl.lock` |
| `tuvl doctor` | `--live`, `--json`, `--only`, `--skip`, `--strict`, `--fix`, `-q`, `--verbose` | Is the project healthy? Runs named check groups, each check ok / warn / fail / skip: `project` (identity record), `env` (Python range, `.env` present and git-ignored, `uv`), `config` (the project loads), `models` (each model, the variables it needs and which are missing; `--live` makes one minimal call per model — Laya/Jev: their `/health`), `storage`, and, where the toolchain is installed, `git` (repository, branch, identity, remote) and `skills` (`AGENTS.md`, `.agents/skills`). `--only` / `--skip` take comma-separated group names. Exit 1 on any failure; `--strict` exits 2 when only warnings remain. `--fix` applies the safe repairs a check offers (`git init -b develop`, adding `.env` to `.gitignore`) and re-checks; nothing destructive. A production server runs the model check at startup and refuses to start on a missing variable; `/health` reports each model's readiness |
| `tuvl test` | `--live`, `--allow-uncertain`, `--strict`, `-k/--only TEXT`, `--json` | Run `Test` documents offline (`--live` lets unmocked model/tool agents call out). Results are PASS, **STUBBED** (expectations met only through unmocked `pending` placeholders — not counted) or FAIL; `--strict` (CI) also fails on stubbed results and untrusted judge calibration |
| `tuvl project info` | `--json` | The project's identity from `.tuvl/project.yaml`: the immutable, self-checking id (`prj_<uuidv7>-<2 check characters>`, minted by `tuvl init`; the check catches typos and hand edits, it is not a signature), name, author, email, type (`poc\|dev\|production`), version, registry status. Also editable in Insight → Settings → Project. Full reference: [project](project.md) |
| `tuvl project init` | `--name`, `--new-id` | Create `project.yaml` for a project that predates it. Never changes an existing id; `--new-id` replaces a malformed or copied id and clears its registration |
| `tuvl project set FIELD VALUE` | | Update `name`, `author`, `email`, `type`, `version`, `description`, `license` or `repo` (validated). The description is Markdown (up to 2000 characters): `VALUE` of `@about.md` reads a file, `-` reads stdin; `project info` renders it |
| `tuvl project register` | `--hub URL`, `-y` | List the project in the public catalogue. Prints the exact payload first and asks; signs in with GitHub's device flow; the author and email are sent for contact and never shown publicly. Also available as Insight → Settings → Project → Register / Update listing (same payload preview and login) |
| `tuvl skills update` | `--diff` | Refresh `AGENTS.md` and `.agents/skills/` to this tuvl version (removes 1.x skills; mirrors to `.claude/skills/`) |

## Specs

| Command | Options | |
|---|---|---|
| `tuvl spec verify [SPEC_FILE…]` | `--strict`, `--no-tests`, `--json` | Does the implementation match the spec? Zero tokens; rules R001–R010 and a traceability matrix (step → agent → tests). Exits 1 on a mismatch (`--strict`: also on unfinished work) |
| `tuvl spec new NAME` | `--owner`, `--workflow` | Write `specs/<name>.md` from the template |
| `tuvl spec import PATH…` | `--title`, `--supersedes`, `--initials`, `--include`, `--exclude`, `--max-size`, `--dry-run`, `--json` | Copy an idea (files or a folder) into `idea/IDEA-<INITIALS>-NNNN/source/` as a numbered, immutable record, with `IDEA.yaml` (file hashes, who, when) and `idea/INDEX.yaml`. Text is extracted from Markdown/text directly, from Word files with no extra install, and from PDFs with `tuvl[pdf]` (a scanned PDF has no text layer and gets a warning; there is no OCR) into `extracted/`. Secret and key files, hidden files, symbolic links and unsupported types are skipped and listed. Ids are `IDEA-SK-0004` → `SPEC-SK-0004-01` → `TASK-SK-0004-01-003`: the spec and task ids inherit the idea's number. Initials come from `.tuvl/agent.yaml` (`--initials` saves them on first use) |
| `tuvl spec ideas` / `idea ID` | `--json` | List the ideas and the specs generated from each / show one idea's files, hashes and specs |
| `tuvl spec renumber IDEA` | `--to IDEA-XX-NNNN` | After two developers picked the same number: give the idea a new one (default the next free) and carry its spec and task ids, file names, links and the task lists' spec hash along. `tuvl doctor` (group `ideas`) reports duplicate ids and an idea the base branch already numbers differently |
| `tuvl spec approve SPEC` / `reject SPEC --reason …` / `reopen SPEC` | `--force` (approve) | Approve a spec (by id, name or file): records who, when and a hash of the body in its front matter; refuses while `spec check` has errors. Editing the body afterwards makes the approval stale (S017). `reject` sends it back to draft with a reason; `reopen` withdraws an approval |
| `tuvl spec tasks SPEC` | `--dry-run` | Derive the task list from an **approved** spec, with no model: one task per new model, step and example, a manual task for each external-system step. Keeps ids, refreshes section hashes, marks removed ones `obsolete`; `--dry-run` previews a draft |
| `tuvl spec list` | `--json` | Each spec's id, status (draft / approved / approved but changed), approver and ideas |
| `tuvl audit log` / `show REF` / `verify` / `export` / `prune` | `--entity`, `--actor`, `--kind`, `--since 2d`, `-n`, `--follow`, `--json` (log); `--format json\|csv`, `-o` (export); `--older-than DAYS` (prune) | The local audit ledger `.tuvl/audit/<YYYY-MM>.jsonl` (git-ignored): one hash-chained event per action with side effects — init, agent choice, idea import, id renumber, spec create / approve / reject / reopen (refusals too, with the reason), task derivation. It holds ids, hashes and short details, never file contents, prompts or secrets (full prompts and agent output go to `.tuvl/trace/` by hash). `--entity` on an idea also shows its specs and tasks. `verify` finds an edited, removed or reordered line (exit 1); `prune` deletes old trace files, never the ledger. The ledger belongs to one machine and one developer: what the team shares through git is the spec's own approval fields |
| `tuvl spec new NAME --idea IDEA-…` | | Also numbers the spec `SPEC-XX-NNNN-NN` after its first idea, links it to the idea(s) and records `status: draft` |
| `tuvl spec gen --idea IDEA-… \| --from PATH` | `--title`, `--agent`, `--max-attempts 3`, `--budget USD`, `--timeout S`, `--model`, `--base`, `--dry-run`, `--show-prompt`, `-y`, `--consent`, `--no-pr`, `--ready`, `--keep-worktree` | A coding agent writes a **draft** spec from an idea. tuvl numbers it (`SPEC-XX-NNNN-NN`), creates branch `spec/<id>` in a worktree under `.tuvl/worktrees/`, builds the prompt (the idea's text, the spec grammar, the rules), runs your agent headlessly, lets it change **only** that spec file (anything else is reverted and fed back), puts back the lifecycle fields it must not set (`id`, `ideas`, `status`, no approval), runs `spec check` and retries with the findings, then commits and, with a remote and `gh`/`glab`, pushes and opens a draft pull request. It never merges and never approves. Needs git; the idea must be committed (`spec import --commit`; `--from` does it). With Claude Code the run is restricted at the source (no code-running tools, files confined to the folder, nothing may prompt); `generic` (`tuvl agent use generic --command '…'`) cannot be restricted, only checked afterwards. Idea text is sent to your agent only after you consent once (`--consent`, stored in `.tuvl/agent.yaml`) |
| `tuvl spec check [SPEC_FILE…]` | `--strict`, `--json` | Is the spec complete and consistent? Zero tokens; rules S001–S016 with line numbers, plus P001–P005 on its task list ([spec-driven](spec-driven.md#2-check-it)). Exits 1 on a blocking finding (`--strict`: on warnings too) |
| `tuvl spec status [SPEC_FILE]` | `--strict`, `--no-tests`, `--json`, `--watch`, `--interval` | Derived task statuses. `--strict` exits 1 unless every live task is done and none is blocked or stale. `--watch` keeps refreshing (recomputing only when a project file changes) and overlays live `codegen` progress (queued, running attempt n/N and its gate, failed, in review) from `.tuvl/live/tasks.json` |
| `tuvl spec diff [SPEC_FILE]` | `--json` | Stale tasks and spec sections no task covers |

## Servers

| Command | Options | |
|---|---|---|
| `tuvl dev` | `-p/--port` (8885), `--auto-login`, `--no-tui`, `--show-key`, `--no-browser`, `--no-tui`, `-H/--allow-host` | Dev server with Insight and the dev API, reloading on YAML changes. The session key is stored in `.tuvl/.dev-session` (0600); `--show-key` prints it. **On a terminal it also starts a terminal UI** (`tuvl[tui]`, part of `tuvl[standard]`): a tree of your ideas → specs → tasks (status, and live progress while `codegen` runs), the actions that apply to what you select (check, approve, derive tasks, scaffold, build with your agent, validate, test, ship…), and three logs: the command you ran, the engine, and the audit trail. Every action runs the same `tuvl` command you would type, so the gates and the audit trail are the same; anything that spends your agent's tokens or is hard to undo asks first (`Run it` / `Cancel`) and says so. `q` quits and stops the engine, `r` refreshes, `x` stops a running command. `--no-tui`, or no terminal (CI, a pipe, ssh without a tty), runs the engine in this terminal exactly as before |
| `tuvl run` | `-p/--port`, `--host`, `-w/--workers`, `--role all\|api\|worker`, `-c/--concurrency` (8), `-H/--allow-host` | Production server. `api` serves HTTP and runs synchronous requests inline; `worker` executes the queue |
| `tuvl mcp` | `--allow-write` | Dev tools for coding agents over MCP (stdio); `--allow-write` adds `codegen_write`, `run_workflow`, `pin_fixture`. Refuses production |

## Runs

These talk to a running server: `-u/--url` (`TUVL_URL`, default `http://localhost:8885`) and
`-t/--token` (`TUVL_TOKEN`, needs `runs:read`).

| Command | Options | |
|---|---|---|
| `tuvl runs list` | `-w/--workflow`, `-s/--status`, `-n/--limit`, `--json` | Recent runs, newest first |
| `tuvl runs get RUN_ID` | | One run as JSON |
| `tuvl runs tail [RUN_ID]` | `-w/--workflow`, `-p/--payload JSON` | Follow a run's events until it ends (or start one with `--workflow`); exits 1 if it fails |
| `tuvl runs pin RUN_ID` | `-n/--name` | Export the journal to `tests/fixtures/<workflow>/<name>.journal.json` |
| `tuvl runs replay FIXTURES…` | `--json` | Re-run pinned journals offline; fail if the end or output differ |

## Shipping and operations

| Command | Options | |
|---|---|---|
| `tuvl ship` | `-t/--tag`, `--no-image` (was `--no-build`), `--push`, `--force`, `--strict`, `--extra`, `--with-laya/--without-laya`, `--format image\|archive\|both`, `--archive-format tar.gz\|zip`, `--out`, `--allow-incomplete`, `--allow-dirty` | Gate (validate, no `pending` agents — V010 is an error at ship time, current lock; then, once the files are written, **the deterministic spec gate**: every spec under approval is approved and unchanged, `spec check` and `spec verify` have no errors, every task is done (`--allow-incomplete`), generated files are current (`codegen --check`, for projects with specs), no C-rule errors in the agents' Python, a current `uv.lock` (an error for the archive), and a clean git tree (`--allow-dirty`; what ship writes itself does not count). A spec with no `status:` only warns), then `.dockerignore` as an **allowlist** (only models, workflows, agents, artifacts, datasources, llms, federation, config, lock and `.tuvl/system.yaml` / `telemetry.yaml` enter the image; specs, task lists, tests, agent rules and skills, compose files and anything else stay out — V027 refuses development files), `deploy/Dockerfile` (pins the locked tuvl version and installs only the extras the project uses: `mcp` for `use: mcp` tools, loop MCP servers and MCP export, `redis` for a redis datasource, `vector` for collections and `tuvl.data_*`, `otel-grpc` for `otlp_protocol: grpc`; it also stops when `agents/*.py` imports a package `pyproject.toml` does not declare. `--extra NAME` adds one the scan cannot see; the choice is recorded as the image label `io.tuvl.extras`) and a Helm chart (`split: true` for api + worker Deployments; a Laya Deployment + Service, with `LAYA_API_BASE` set for the engine, when a model uses `provider: laya` or with `--with-laya` — `laya.enabled` in values.yaml) and `docker build`, labelled `io.tuvl.runtime-hash` (one sha256 over the runtime files) and `io.tuvl.git-commit`. **`--format archive`** instead writes `dist/<name>-<version>.tar.gz` (or `.zip`) plus a `.sha256`: the same runtime files with `run.sh`, `RUN.md`, `.env.example` and `BUILD-INFO.json`, reproducible byte for byte from the same files, for hosts without Docker. On the host: `tar xzf …`, `cp .env.example .env`, fill it in, `./run.sh` (needs `uv`; it installs the locked dependencies and `tuvl==<locked>` with the same extras as the image, and serves on port 8885) |
| `tuvl deploy` | `-d/--project-dir` | Coming soon: deploy to a hosted, managed tuvl engine that runs your backend services. Today it prints a message, deploys nothing and exits 1 |
| `tuvl keys generate` | `-w/--write`, `-f/--force` | A persistent Ed25519 key for signing access tokens (`TUVL_SIGNING_KEY`) |
| `tuvl db generate-rls` | `-o/--out` | Idempotent row-level-security SQL for tenant-scoped tables |
| `tuvl db check-rls` | | Exit 1 if a tenant-scoped table lacks its RLS policy |

### Extras: what an image installs

`tuvl` installs lean. Features with their own packages are extras, and `tuvl ship` reads the project and
installs `tuvl[<only those>]==<locked version>`:

| Extra | Package | `tuvl ship` installs it when |
|---|---|---|
| `mcp` | `mcp` | a `use: mcp` tool, a loop `mcp` tool, or a workflow with `trigger.mcp.enabled` |
| `redis` | `redis` | a `kind: DataSource` with `type: redis`, or `agents/*.py` imports `redis` |
| `vector` | `pgvector` | a Collection or Embedding document, `tuvl.data_search` / `tuvl.data_ingest`, or an import of `pgvector` |
| `otel-grpc` | OTLP gRPC exporter | `.tuvl/telemetry.yaml` has `otlp_protocol: grpc` |
| `codegen`, `test` | `libcst`, `aiosqlite` | never: `tuvl codegen`, `tuvl init --sample` and `tuvl test` are development tools |

`tuvl[standard]` installs Insight and every extra, so a development install needs nothing else. The
model providers and blob storage (S3, Azure, GCS, local) are part of `tuvl` and need no extra.

`tuvl ship` prints the extras it chose and why and records them as the image label `io.tuvl.extras`
(`docker inspect` shows what an image carries). Beyond the extras:

- It also scans `agents/*.py`: an import of a package that `pyproject.toml` does not declare aborts the ship,
  because the image would fail at run time. Declared packages that no agent imports are listed and kept.
- `--extra NAME` adds an extra the scan cannot see, for example a feature switched on by an environment
  variable. It accepts `mcp`, `redis`, `vector` and `otel-grpc`.
- A kept `deploy/Dockerfile` (no `--force`) that lacks an extra the project now needs stops the ship.
- Using a feature without its extra fails with `pip install 'tuvl[name]'`; the same message appears for
  `tuvl codegen`, `tuvl test` and `tuvl mcp` on a bare install.
- `tuvl deploy` is for managed hosting and is not available yet: it prints a message and exits 1.
  Until then, install the chart `tuvl ship` writes with `helm`.

## The CI gate

```bash
tuvl spec check && tuvl validate --strict && tuvl codegen --check && tuvl lock --check && tuvl test --strict && tuvl spec verify --strict && tuvl spec status --strict
```
